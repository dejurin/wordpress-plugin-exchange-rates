# Exchange Rates 1.4.0 — concurrent source-selection acceptance

Validation date: 2026-10-18. Base main: `5bd213eee85ae081296153d2bbca89610b64ad65`. This scoped report does not authorize merge or publication. WordPress.org SVN remains read-only.

## Defect and behavior

A slow request for source A could finish after an administrator selected source B. The old request wrote its complete settings array and payload, reverting the selection, preferences, availability and newer rates. Both successful and failed old responses could overwrite state. This race was also reproducible in published 1.3.2 during the preceding acceptance.

The updater now captures the serialized settings directly from the database before HTTP. It conditionally writes the payload and service metadata only while those settings still match. A source or preference change rejects the obsolete result. The successful newer payload stays intact; when B failed, the last good payload and its original attribution remain intact while B stays selected for the next retry.

Each write checks both the selected settings and the previous target value within the SQL statement. A PHP comparison followed by ordinary `update_option()` leaves a check/write race; cache invalidation alone does not close it. The first insertion uses a conditional insert without an upsert, so an old worker cannot replace a newly created cache. No lock is held across the provider request.

The request source, merge input and old-value notifications use persisted snapshots. Reading a stale `alloptions` value after taking a database snapshot would otherwise allow a mismatched source to pass the write guard. The final readback also checks storage directly.

The private helper is limited to this service's two option records. It invokes sanitizers and pre-update veto filters, emits notifications for successful writes, invalidates the affected option caches, and treats an exact unchanged value as success. A filter that changes the requested validated value causes a failed update rather than an unverified write. Runtime `option_*`/`pre_option_*` read overrides do not replace the persisted selection used by the updater; the existing explicit source argument remains supported.

## Compatibility, limits and rollback

Only `UpdateDataSources.php` and the 1.4.0 changelog change inside the installable plugin. No public signature, version, option key, stored schema, shortcode, widget, CSS, JavaScript, dependency, hourly schedule, five-minute retry or frontend AJAX behavior changes. Existing 1.3.2 saved data stays readable in both directions. The canonical checkout's unrelated README edit and untracked browser files were preserved and excluded.

Rejecting the entire obsolete result is intentional even if only a display preference changed during HTTP; the existing retry can refresh the selected source later. The two option writes are individually conditional, not a transaction spanning both records. This fix prevents obsolete-source writes; it does not serialize every possible same-source manual/background writer or arbitrary third-party direct SQL. Stale cache behavior is injected deterministically; this is not a Redis integration certification. Synthetic success does not establish live-provider uptime, and this scope does not certify every theme, cache backend, database version or physical browser/device.

Revert this PR through a reviewed change to roll back the guard; no data migration is necessary, but the known source-selection race returns. The existing final ZIP from main does not contain this fix until the PR is reviewed, merged and rebuilt. Do not publish that older ZIP as if it included this change.
