# Exchange Rates 1.4.0 — release acceptance

This report is a historical snapshot of the initial candidate. Later README, RTL and SVG changes supersede its archive identity. See the [2026-10-16 CSS cleanup acceptance](1.4.0-css-audit.md) for the post-#14–#16 reference, current cleanup scope and its own evidence; the results below apply only to the payload identified here.

Validation date: 2026-10-15. This report prepares a release; it is not a publication record. WordPress.org SVN remains read-only. The maintainer froze functionality at the already merged PRs #5–#10 and deferred additional bug fixes until after 1.4.0.

## Scope and exact artifact

- Published baseline: Exchange Rates 1.3.2, immutable Git import `e2fa9407b8068a3c8b34400a938da4962d30c43f`.
- Frozen implementation: `14773950376e14a9b0a9e97d1abf54ac8ef2a936`.
- Release metadata commit: `2e05c11f983b0d16fc6d5eec994da5047050d44b`. Subsequent acceptance-documentation commits do not change the plugin payload.
- Candidate archive: `exchange-rates.1.4.0.zip`, 926 files, SHA-256 `e8523263f711ead5ec51227ea800d17182cb473eb0fa63753451e94e6480f158`.
- Official 1.3.2 ZIP: 926 files, SHA-256 `1db5b5f74d5d42f43f495a3d85ce23fa8d140c0e87313321fe7a15c1e450a97f`. Every file matches the immutable baseline manifest.

Only the plugin header/docblock, runtime version/docblock and readme metadata/release notes differ from the frozen implementation. All other plugin bytes are identical. Existing namespaces, option keys, shortcode attributes, widget identifiers, installation path, translations, dependencies and declared WordPress 5.6 / PHP 5.6 minimums remain unchanged. No data migration is added.

The included fixes preserve integer zeros at zero precision; isolate table recalculation; associate settings labels while retaining Sources navigation; keep administrative JavaScript variables local; compare the manual-update cooldown in UTC; and persist validated update metadata with readback and honest unknown-time handling. This release does not fix every issue present in 1.3.2.

## Cache requirements

Fresh HTML correctly changes public and administrative JavaScript URLs to `?ver=1.4.0`; real warmed browser caches fetched the new bytes without a manual browser-cache clear. A controlled page cache retaining old 1.3.2 HTML continued to request old cached JavaScript and reproduced the old cross-table recalculation bug. Purging the HTML cache restored independent tables in that same browser.

Autoptimize's tested default minify/defer and aggregate profiles both passed with a real Redis cache. The aggregate JavaScript changed from `autoptimize_6182072604f8d3ce1e4a45792a4a3045.js` to `autoptimize_dee483224defb1821a82d944a96b98ed.js` during the warm upgrade. This does not override the separate stale-HTML result or establish compatibility with every optimizer option.

Before accepting an update, purge the relevant page/CDN HTML caches and regenerate optimizer bundles, then verify the requested asset version and behavior. See the [upgrade procedure](../release.md#updating-a-site-with-caches). The local cache model is not evidence of testing an owner's external CDN configuration.

## Known issues deferred after 1.4.0

1. **Failed source switch and retained cache.** If a newly selected source fails, old rates can be interpreted using the new source's direction rules and attribution. The real 1.3.2 and frozen-candidate browser flows reproduced USD→EUR changing from 1.25 to 0.8 while retaining the old payload. Correctly persisting failure availability does not resolve this separate rendering issue.
2. **Localized amount input.** The unchanged table input parser uses `parseFloat()`. A formatted amount such as `1,000` or `1 000` can be truncated to 1. PR #5 fixes initial integer formatting, not locale-aware input parsing. Both baseline and candidate reproduce the problem.
3. **Apostrophe presentation.** The initial price cell may use a curly apostrophe while its input and JavaScript recalculation use a straight apostrophe. Fresh baseline and candidate browser checks reproduce the same representation; this is not a newly introduced difference.
4. **State/concurrency limits.** Rate payload and metadata are separate writes, without a transaction, cross-request lock or failure backoff. Rejected writes are reported, but the checks do not establish atomicity or arbitrary concurrent-request safety.
5. **Unknown update time.** Missing/zero time intentionally means no known successful update, does not fabricate a date and does not trigger the page-load hourly fallback on every visit. Cron or manual update must recover that state. Positive expired timestamps retain the existing hourly fallback.
6. **Block-widget shortcode generator.** In the tested block Widgets interface, generated-shortcode textareas remain empty on both 1.3.2 and 1.4.0. Saving/reloading the actual widgets works. The classic interface generates its shortcode. This pre-existing editor integration issue is deferred.
7. **Incomplete translations.** For example, Formatting remains English in the installed Ukrainian catalog on both baseline and candidate. Saved user-authored English column labels are also retained rather than overwritten. No translation rewrite is part of this release.

## Acceptance boundary

The owner selected isolated test environments because no representative real-site clone was available. A finite matrix does not prove compatibility with every theme, host, cache/CDN policy, multisite configuration or third-party plugin. Known pre-existing defects are recorded rather than silently treated as successes or fixed beyond the frozen scope.

Unverified boundaries include physical mobile devices, native 200% browser zoom, assistive technology, multisite, arbitrary simultaneous refresh requests, other providers and third-party combinations, external/query-stripping CDN policies and a production backup restoration. These are not reported as passed. This release preparation also does not constitute a fresh full security or WPCS audit.

## Local environment incident

The initial minimum-runtime launcher omitted an explicit Compose project argument. An existing env-file overrode the intended project name, recreating the ordinary local WordPress container and restarting its database instead of creating an isolated test environment. The runtime entrypoint copied a test MU-plugin and assigned file ownership; no WordPress installation, test, SQL command or HTTP request had been run by that agent before the mistake was identified. That attempted run contributes no acceptance evidence.

Automatic approval review blocked stopping the ordinary container. After the owner explicitly approved the recovery plan, the coordinating agent retained private database/site backups, quarantined the test MU-plugin and restored the original pinned WordPress/PHP image, port, subnet and both named volumes. Core/config hashes and logical database dumps before/after recovery matched. Per-file ownership was not inventoried before the incident, so exact prior ownership cannot be independently proven.

The minimum-runtime test was restarted using a new explicit project, uniquely named volumes, an unused subnet/port and an entrypoint that rejects pre-existing unmarked WordPress data. All reported minimum-runtime results belong only to that corrected isolated environment. The other two agents' project/volume identities were independently checked and were correctly isolated throughout. Recovery receipts are retained privately; no SVN writes or WordPress.org publication occurred.
