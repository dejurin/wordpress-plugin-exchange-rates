# First-load manual recovery and uninstall documentation

## Problem and change

After the first failed rate request, the general settings page hid `Force Data Update` because no current rates existed. Its message incorrectly directed the administrator to `Save`; saving an unchanged source does not request rates. The existing AJAX handler already supports retries with a missing or zero success timestamp.

The button and its existing response container now render outside the rates-availability condition. The button has an explicit `type="button"`. The empty state uses the existing translated `No data received` message. No update handler, public JavaScript, CSS, storage format, cron hook, nonce, capability or cooldown behavior changes.

The README explains manual retry and the existing lifecycle contract:

- Deactivation preserves settings, widget configurations and saved rates.
- Deletion through WordPress removes plugin settings, both widget configurations, saved rates and cached source information. It does not edit posts or pages.
- Reinstall/upgrade/rollback must replace files without uninstalling to preserve configuration. Back up the database before deletion.

Two unused and misleading Save instructions were removed from POT/PO/MO. All 503 surviving translations per locale are preserved, including placeholder and HTML parity. No new translation keys were introduced.

## Tests before implementation

Commit `ff95f4a` adds the regression before modifying plugin files. All four new cases failed because `#exchange-rates-force-data-update-button` did not exist. They use real WordPress admin requests and the existing authenticated AJAX endpoint; only the external provider response is synthetic.

`tests/browser/first-load-update.spec.js` covers LTR/RTL at 390 and 1280 CSS pixels:

1. A real service request fails with no saved rates and a zero success timestamp.
2. The administrator can retry without changing source/settings.
3. Another provider failure leaves rates absent, preferences/widgets unchanged and the button usable.
4. A successful retry saves validated rates and metadata and reloads the page.
5. An immediate second request is denied without calling the provider.
6. A later failure preserves saved rates and the last successful timestamp.

The fixture restores its settings, rates, widget and scheduling snapshots after each case. Authentication traces/screenshots are disabled and its failure artifacts are excluded from CI uploads. Outbound WordPress HTTP is blocked by the local fixture. Core RTL CSS is explicitly selected and asserted; merely changing HTML direction produced mismatched LTR admin CSS during fixture development and was corrected in the test harness. No forced clicks or plugin CSS overrides are used.

## Translation test harness correction

The existing `wp eval-file` catalog check used a repository-relative path despite tests being mounted under `/opt/tests`, and its local counters were different from the globals incremented by assertion functions. It could print failures followed by `PASS: 0 localization assertions` and exit successfully. The check now resolves the installed plugin via `WP_PLUGIN_DIR` in WordPress and explicitly shares its counters. A missing extraction is required to fail with a nonzero exit code in CI. Positive runs above validate the actual catalogs, not just process success.

## Reproduction and evidence

Use the disposable environment described in [development.md](../development.md), never the ordinary development database. Run `first-load-update.spec.js` and `manual-update-state.spec.js` with its explicit `WP_TEST_URL` and Compose project, followed by the seven PHP integration suites listed above. CI runs these browser tests automatically and checks both valid and missing catalog extractions.

Local receipts are in the ignored `dist/first-load-review/`: `red.log`, `green.log`, `min-browser.log`, integration/localization logs and `min-*-state.log`. Private Compose configuration and credentials are not committed. The tested candidate ZIP is a test artifact, not a published release. The canonical checkout's unrelated changes were checked against their previous hashes and retained.

## Scope and rollback

This PR is based on `codex/release-translations` (PR #28), following the unmerged source-validation/documentation/translation chain. It does not merge or publish those PRs. Revert this PR to restore the previous settings-page presentation and wording; no database rollback is needed. Existing uninstall behavior is unchanged.

This is bounded compatibility evidence, not a guarantee for every theme, plugin combination, real API outage or network configuration. Browser checks use Chromium and synthetic provider responses. Response-size limits and the previously documented in-flight deactivation retry question are outside this change. WordPress.org SVN remains read-only; nothing is published.
