# 1.4.1 native cron retry correction

Prepared locally on 2026-10-20 after the first three-hour live observation.
The base is merged PR #31, commit `eb1e91fe6801144d89bc80e300e9b1cb77f9145a`.
The correction remains on a local focused branch; PR submission, merge and
publication are deferred under the user's current instruction.

## Cause and minimal change

Native `wp-cron.php` snapshots all ready events before dispatching them. A
successful recurring refresh cleared every retry, including one still present
in that snapshot. Core subsequently tried to unschedule the missing retry and
reported `could_not_set`. An already-fresh retry could similarly erase a second
overdue retry. This error alone did not mean that the successful rates write failed.

Remove the two `wp_clear_scheduled_hook()` calls from `run_retry()` and successful
`refresh()`. WordPress retains ownership of each due event's removal. A future
retry stays scheduled until its normal callback checks freshness; fresh data
causes no provider request. Successful refreshes still reset failure backoff.
Deactivation still clears both hooks. The 1800-second recurrence, 300-second
failure retry/lease, manual cooldown, settings and data shapes are unchanged.
No new UI strings or translation source references are introduced; POT/PO/MO
remain unchanged and are verified against a newly extracted source POT.

## Tests first and verification

Regression commit `1846134` precedes the fix. The new suite invokes the actual
native cron runner in isolated child processes with synthetic provider responses.
Before the fix it failed 5 of 38 assertions on WordPress 7.1.3 / PHP 8.3.35 and
3 of 38 on WordPress 5.6 / PHP 5.6.40. Both exposed removal of already-deleted
events; only newer core logged `could_not_set`.

The PHP 5.6 interval fixture initially failed the 1799-second boundary because
plugin bootstrap had already resolved native `time()` before the test clock was
loaded. It now supports `--skip-plugins=exchange-rates` and explicitly loads the
plugin after that clock. No production timing logic changes. The old WP-CLI POT
generator also needed an explicit `php -d date.timezone=UTC` to avoid environment
warnings; the plugin's UTC behavior is unchanged.

Local `scripts/plugin.py check`, `lint` and `package` validate metadata, all
56 shipped PHP files and all 929 ZIP entries. Browser/CSS behavior is unchanged;
the previous visual matrix was not rerun. Remote CI has not run for this local
correction. The corrected ZIP SHA-256 is
`53f0a3d8407000dab9c644c4f9fd73ed0b2b3ec9959896c23352184399b51e8d`.
Red/green and runtime logs are retained under the primary checkout's
ignored `dist/cron-retry-141-20261020/` directory.

## Live observation and rollback

A new, isolated three-hour live-provider observation uses the corrected ZIP,
native page-triggered cron and minute-by-minute snapshots. Its own run directory
records exact ZIP/code hashes, start/deadline, provider responses, persisted
success times, rate hashes, cron state and diagnostics. A bounded macOS
`caffeinate -i` assertion prevents idle system sleep; lid closure/manual sleep
remain outside that assertion and any coverage gap makes acceptance incomplete.
The result is pending until the full window and six subsequent cycles complete.
The prior failed/incomplete observation and every 1.4.0 monitor are preserved.

Rollback this correction by reverting its plugin change; no database migration
is needed. That restores the known premature retry-removal defect. Do not replace
code during the live observation or restart its clock to conceal a failure.
