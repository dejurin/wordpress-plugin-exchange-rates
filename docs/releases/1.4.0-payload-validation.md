# Exchange Rates 1.4.0 — API payload validation acceptance

Validation date: 2026-10-18. Base main: `f6299987833f9162ea017b04db6a3c72ff1f9168`. This scoped change does not authorize merge or publication. WordPress.org SVN remains read-only.

## Defect and change

The prior validator accepted a response after finding just one positive numeric rate. Other current/previous rates could be invalid or non-finite, the source could differ from the requested source, and dates could be absent, invalid or relative. A response accepted as successful replaced valid saved data and advanced success metadata. Non-finite rates could subsequently fail conversion arithmetic. These weaknesses were inherited from 1.3.2.

The update service now supplies its requested source to `RatesData::validate_payload()`. Before any rates write, the validator requires a known matching source, string base metadata with a usable base rate, absolute valid dates, and positive finite current/previous rates with representable reciprocals and cross-rate ratios. A malformed supplied previous close rejects the whole update; it is not silently dropped. Missing, null or empty previous-close records remain supported.

Invalid responses take the existing explicit failure path: retain the complete previous payload, source/base, original dates and last successful timestamp; record `rates_available=false`. Background failures retain the existing five-minute retry and lease cleanup. Empty-cache failure retains the existing unavailable-data message. Later valid responses recover normally.

Numeric strings, current-only providers and absolute ISO, SQL and RFC dates remain supported. Dates are validated without rewriting their strings. PHP's calendar-normalization warnings, relative expressions, null bytes, invalid offsets and inconsistent RFC weekdays are rejected. The numeric offset check accounts for [PHP's documented date_parse change from minutes to seconds in PHP 7.2](https://www.php.net/manual/en/function.date-parse.php).

## Compatibility and limits

No database migration, option/key rename, shortcode/widget change, UI/CSS/JavaScript change, dependency update or version bump is included. `validate_payload($payload)` remains callable with one argument; the new expected-source argument is optional. Existing saved payloads are not validated retroactively or rewritten. Reading an individually unsafe non-finite cached rate now returns the existing unavailable-rate value instead of allowing dangerous arithmetic. This does not repair every historically corrupted cache or change the legacy date fallback for already saved malformed metadata.

Stricter rejection is intentional for malformed new responses, including one bad current/previous rate among otherwise valid values. Retained data can remain old while the provider is invalid; its original attribution/date must remain intact. This patch does not add a public stale banner, change converter-caption behavior, parse locale-formatted user amounts, serialize manual/background writes, or certify all themes, caches and browser engines. Unused extra API fields remain untouched; validation covers current and previous-close records consumed by the plugin.

## Rollback

Revert the two production PHP changes through a reviewed PR; no data restoration or migration is necessary. That rollback restores the old validation weaknesses. Existing valid data is stored unchanged and can still be read by 1.3.2. Keep the final package/source revision tied to its reviewed commit, and perform publication separately; nothing here writes WordPress.org SVN.
