## Behavior and compatibility

Page bootstrap schedules work and does not call the exchange-rate provider. Saved rates and their original date remain available after provider failure. The existing hourly hook and frequency are retained. A separate single retry event recovers expired or missing data; failures back off for five minutes. A per-site atomic database lease prevents overlapping background fetches and recovers after a terminated worker. The existing service remains responsible for response validation and persistence.

There is no new frontend AJAX, polling, CSS or JavaScript. An already open page keeps the rates with which it loaded. Newly persisted rates appear on the next uncached request. Empty-cache renderers share the existing translated unavailable-data message.

Existing option payloads, shortcode attributes, widget IDs, source selection, manual-update cooldown, administrator endpoints and activation behavior are preserved. The internal lease option and retry transient do not migrate or rewrite existing user data. Deactivation removes scheduling state, preserving settings and rates.

## Upgrade and rollback

On an isolated WordPress 5.6 / PHP 5.6.40 site, settings, rates, both native widget option arrays, sidebar assignments and a page containing all three shortcodes were saved under the actual published 1.3.2 files. Only plugin files were replaced for:

`1.3.2 → candidate 1.4.0 → 1.3.2 → candidate 1.4.0`

At every stage, all five saved options and the shortcode content match the original values and types. The three shortcodes and both saved native widgets render without PHP warnings or unavailable-data errors. Saved-state SHA-256 remains `3802d9c6329433fdb51d22e14539ae088ce11042688446b26ab8d0da2f5492de`.

Separately, a native table and three pages seeded under 1.3.2 on WordPress 7.1.3 retain their saved state after upgrading and after the full Chromium suite. Intentional display changes already accepted in earlier 1.4.0 PRs are not treated as regressions of this background patch.

For an operational rollback, deactivate the candidate to clear its internal scheduling state, replace plugin files with the verified 1.3.2 archive and reactivate. No data migration is necessary. Reactivation retains the old plugin's explicit initial update behavior, and rollback reintroduces synchronous frontend fallback and the other known 1.3.2 defects.

## Limits and deferred concerns

- WP-Cron normally depends on site requests. Visitor-independent updates require an external/system scheduler. Disabled cron or broken loopback requests leave cached rates stale; this patch deliberately does not fall back to blocking provider calls in the page request.
- Full-page/CDN caches require their own invalidation/expiry policy. Redis-specific acceptance was not repeated for this patch; the refresh lease uses the database rather than an object-cache mutex.
- Explicit administrator/manual/source-change updates retain their existing synchronous behavior and do not share the background-worker lease. This patch does not serialize every possible service caller or change the established failed-source-switch policy.
- Rate data and success metadata remain separate existing option writes, not a new transaction. Existing rejected-write regression tests remain in place.
- Synthetic providers prove failure/recovery behavior, not live-source availability. This pass does not certify every theme, browser, hosting cron configuration or upstream source.

Only dedicated disposable projects on ports 19264/19265 were used; ordinary development and open gallery environments were not modified.
