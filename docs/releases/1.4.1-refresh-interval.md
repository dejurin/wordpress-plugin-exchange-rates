# 1.4.1 fifteen-minute refresh acceptance

Validated on 2026-10-19 from main `55e4cfcb99d140d7f4f48d6b232d630fafcb661a`.
This is a pull-request candidate, not a published release.

## Behavior and scope

One 900-second constant controls the recurring schedule and cache expiry
(`age >= 900`). Existing default hourly events migrate during normal bootstrap,
without reactivation. Migration keeps the earlier due time, creates a replacement
before removing obsolete events, checks failures and retries incomplete cleanup.
It uses the existing per-site lease and rereads cron after acquiring ownership.
A matching schedule name with an obsolete stored interval is repaired as well.

The hook, legacy callback, explicit-source arguments, option keys and stored rates
remain compatible. The source-directory TTL, manual cooldown (60 seconds), error
retry and lease (300 seconds) remain unchanged. Rendering still performs no
synchronous rate request. No frontend assets or service write logic changed.
The schedule label is translated in en_US, uk and bg_BG; POT/PO/MO and version
metadata are synchronized. PHP 5.6 and WordPress 5.6 remain the minimums.

## Limits and rollback

WP-Cron depends on traffic or an external runner. Cached HTML and already-open
pages can continue showing old values. Synthetic tests do not establish API
capacity, real-provider availability or all third-party scheduler behavior.
At 800 sites, 76,800 regular requests/day is an estimate; retries, manual requests
and bursts are additional. No production load measurements were performed.

WordPress cron option writes are not transactional with arbitrary external
writers. A failed cleanup can temporarily leave duplicate work; subsequent
bootstrap retries it. The pre-existing in-flight-worker/deactivation race remains
out of scope: a worker can recreate a retry after deactivation.

For rollback, let in-flight work finish, deactivate 1.4.1, replace plugin files
with the verified 1.4.0 artifact, reactivate and verify hourly scheduling and both
hooks. Preserve rates, settings, widgets and posts. Merely replacing active files
does not guarantee restoration of the old recurrence. No SVN writes, deployment,
merge or publication is authorized by this report.
